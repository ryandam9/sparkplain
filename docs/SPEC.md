# sparkplain — Design Specification

The current design. How it got here (phase plans, live checks, dated decisions) is in [HISTORY.md](HISTORY.md).

## 1. Overview

**sparkplain** is a Go CLI that turns one Spark application's logs into a plain-language HTML report, a JSON export and an interactive explorer page: what ran, on which nodes, with how much CPU, memory and storage, under which identity, and what went wrong. The target is Amazon EMR on EC2 7.3.0 and later (Spark 3.5.1 and newer), running or terminated clusters, with logs in S3 or on local disk.

**Problem.** The Spark History Server shows raw lists per tab. It does not say which node hosted which executors, how memory moved over time, what identity touched Hive, HBase or S3, or why a run failed; answering that means reading container logs by hand.

**Goals**

- One command, one application ID, one self-contained report.
- Every metric explained in plain words; every finding with a severity, evidence (file and line, or an API call) and a fix.
- Fetch everything itself from S3 and read-only AWS APIs, with no other tools and no cluster changes.
- Degrade, don't fail: a missing source is named and its sections marked, and the run still produces a report.

**Non-goals:** live monitoring or alerting; EMR Serverless and EMR on EKS (different log layouts); changing clusters or jobs; cost in dollars; Kerberos and authorization failures in HBase.

## 2. Inputs and fetching

**Input modes**

| Mode | Command | Reads |
| --- | --- | --- |
| Event log only | `-app-id … -eventlog <path>` | The event log: local file, rolling `eventlog_v2_*` folder, folder of logs, History Server zip, or `s3://` object or prefix |
| Online | `-profile … -cluster-id … -app-id …` | The EMR, EC2, CloudWatch, CloudTrail and STS APIs, and the cluster's logs under `<LogUri>/<cluster-id>/` in S3 |
| Offline | `-from <dir> -app-id …` | A local copy of the cluster's log folder (`containers/`, `steps/`, `node/`), a folder of such copies (the one holding the application wins), or one application's `container_*` folders; no AWS calls |

**Finding the event log.** The event log is optional (on EMR it defaults to HDFS and dies with the cluster). In order: `-eventlog`; `eventlog-prefix` in the config file; the cluster's `spark.eventLog.dir` when it is on S3; any S3 `spark.eventLog.dir` the cluster's steps set in their own `spark-submit` arguments, newest first. Without one, the run continues on the logs and APIs, marks the sections that need it, and exits 3.

| Event log input | Handling |
| --- | --- |
| S3 prefix | Lists only `<prefix>/<app-id>*` and `<prefix>/eventlog_v2_<app-id>*` |
| S3 object | Reads that object; a location without a trailing `/` is checked as an exact key first, then as a prefix |
| Local file | Plain, `.lz4` (lz4-java block stream), `.zstd`, `.snappy` (snappy-java stream) or `.inprogress` |
| Folder | A rolling log (parts in order), or a folder of logs, where the highest attempt wins, preferring finished logs |
| History Server zip | The Download zip, unpacked in memory within limits. Given as a file, or as the folder it was saved in (`eventLogs-<app>.zip`, `eventLogs-<app>-<attempt>.zip`, or a browser's ` (1)` copy; the newest when there are several), by `-eventlog` or a local `eventlog-prefix`. A leading `~/` in paths from flags or the config file is the home folder |

`-app-id` must match the ID inside the event log (a mismatch exits 2). A zip with several logs, none named after the application, is "not found"; a log whose name does not match and that has no application start event is refused.

**Fetching rules**

| Rule | How |
| --- | --- |
| Explicit identity | `-profile` required online (`default` for the default chain); region from the profile unless `-region`; each bucket's region found with `HeadBucket` |
| Scoped listing | Only `containers/<app-id>/`, the steps that may have submitted the application, and `node/<instance-id>/` for the nodes it ran on plus the primary node; never the whole cluster. The exception is `node/*/applications/hbase/` on every node that was up during the run, since a region server can serve the application from a node that ran none of its executors; nodes that ended before the run or joined after it are not listed (`ListInstances` names every instance a cluster ever had) |
| Time window | HBase logs hold every application's hours: hourly files outside the application's time are skipped and other lines dropped. The window comes from the event log; else from YARN's application summary in the ResourceManager log (its exact start and finish); else from the first and last times the application's container logs carry, on any line that starts with a time (`2026-10-02 05:12:03,123`, its ISO form, or Spark's `26/10/02 05:12:03`), whatever log4j pattern follows; else from the step that submitted it. Lines are read in Spark's own layout (`26/10/02 05:12:03 INFO Executor: …`), Hadoop's and EMR's (`<time> <LEVEL> <logger>: …`), HBase's daemons' (`<time> <LEVEL> [<thread>] <logger>: …`), and the thread-first layout (`<time> [<thread>] <LEVEL> <logger> - …`, log4j `%d [%t] %-5p %c - %m`). The HBase row names the window and where it came from. AWS queries use the window padded by `-window-pad` (5 min) |
| Streaming | `.gz`, `.bz2`, plain and bounded `.zip`; every file streams straight into its parser, no temporary files |
| Bounded | Worker pool (`-workers`, 16); stored size per object (`-max-size`, 10 GiB); unpacked size per object, part or zip entry (`-max-unpacked`, 50 GiB); zips in memory (256 MiB each, 1 GiB at once); 1,000 entries per zip; event log lines up to 256 MiB; log lines cut at 64 KiB; `-overall-timeout` (30 min). A file cut short is marked partial, never passed off as complete |
| Consistency | `GetObject` with `If-Match` on the listed ETag; unrestored Glacier and Deep Archive objects are reported, not read |
| Error classes | `accessDenied`, `notFound`, `throttled`, `timeout`, `archivedUnavailable`, `corrupt`, `tooLarge`, shown in the Sources panel |
| Read-only | Only List, Get, Describe, Head and Lookup calls, and `sts:GetCallerIdentity` |

**Access check.** Every run starts by checking every access it will need, before reading anything, with small read-only calls made in parallel (15 s each), and prints one line per source. Online: who the credentials are (`GetCallerIdentity`); the EMR API (`DescribeCluster`, `ListSteps`, `ListInstances`, `ListInstanceGroups` or `ListInstanceFleets`, `DescribeStep` on the newest step, and `DescribeSecurityConfiguration` when the cluster has one); each log folder (container, step, node, and HBase when the cluster runs it, checked on the primary node) by listing one object and reading its first byte (a ranged `GetObject`), since a bucket policy can allow `s3:ListBucket` and refuse `s3:GetObject`, and a KMS-encrypted object fails only when read; where the event log will come from (`-eventlog`, `eventlog-prefix`, the cluster's `spark.eventLog.dir`, or a step's; an HDFS one is marked unreadable, with how to supply the log), listed and read the same way; the newest step's script on S3, read as the run reads it (`GetObject` alone); CloudWatch `ListMetrics` and `GetMetricData` (separate permissions), EC2 `DescribeInstanceTypes` and CloudTrail `LookupEvents`, unless turned off. Offline it checks the `-from` folders. Both check that `-source` paths exist and that the output folder can be written (without writing to it), which would otherwise fail only at the end. A readable folder with nothing in it yet is told apart from a refused one. A line that fails gives the error class, what it needs and an `aws` command that repeats the call. The run then reads every source as usual; the rows go into the JSON as `accessCheck`. `-check` stops after the check (exit 0 all readable, 3 not).

## 3. Data sources

No single source answers every question, so sparkplain joins them on cluster ID, application ID, container ID, host name and time.

| Source | Where | Provides |
| --- | --- | --- |
| Spark event log | `spark.eventLog.dir` | Application, executors (host, cores, removal reason), jobs, stages and tasks (time, CPU, GC, spill, shuffle, I/O, locality), per-stage executor memory peaks, cached data, SQL plans and operator metrics, the full configuration and classpath |
| Container logs | `containers/<app>/<container>/std{out,err}` | The driver's lines about jobs, stages, tasks and executors (rebuilding the run without an event log, below); each task's own lines in its executor's log (its story, below); exceptions and tracebacks, out-of-memory, memory kills and exit codes, lost executors, access errors, Kerberos, metastore and HBase lines, HBase table use and retries, each `TableInputFormat` task's split and its size, a `sparkplain-scan` line (decoded), missing classes, the jars YARN localized |
| Step logs | `steps/<step>/{controller,stderr,stdout}` | The `spark-submit` command (redacted), the application it submitted, the step's status, YARN's final report; its stdout (in client mode, what the driver printed) for the step that submitted the application |
| Node logs | `node/<instance>/…` | NodeManager and ResourceManager lines for the application's containers, each node's YARN capacity (from its registration line, else from the lines placing the application's containers on it: memory in use plus memory left), bootstrap actions. A node that ran part of the application with neither line in the logs read is named under the node chart, never left out silently |
| HBase server logs | `node/<instance>/applications/hbase/hbase-hbase-{master,regionserver}-<host>.log[.<yyyy-mm-dd-hh>].gz`, on the nodes up during the run, only for the application's hours, from the time window above (for an HBase cluster of its own too). With no window at all, none is read, since every hour the cluster ever logged would qualify. Hours outside the run are counted in the Sources row, not listed one by one | Region moves and splits, a lost or stopped region server, writes refused, scanner leases dropped, flushes, compactions, pauses, slow calls |
| EMR API | `DescribeCluster`, `ListSteps`, `ListInstances`, `ListInstanceGroups`/`Fleets`, `DescribeStep`, `DescribeSecurityConfiguration` | Release, applications, log URI, configuration, nodes with type, group and market, roles, security posture |
| EC2 API | `DescribeInstanceTypes` | vCPU and memory per instance type |
| CloudWatch | `AWS/ElasticMapReduce`, `AWS/EC2`, `CWAgent` | Containers pending and allocated, YARN memory free, other applications running, node CPU; node memory and disk only with the CloudWatch agent |
| CloudTrail | `LookupEvents` by each node's instance ID | AWS calls made from the application's nodes and every refusal |

**Joins.** Container logs join executors (and the driver) through the `CONTAINER_ID` attribute YARN gives Spark; hosts join EMR instances by short host name (`ip-10-0-2-10.ec2.internal` matches `ip-10-0-2-10.us-east-1.compute.internal`); steps join the application through the ID in the step's `stderr`; HBase server events join the HBase stage running at the time.

**Without the event log: the run rebuilt from the driver's log.** In cluster mode the driver runs in the application master's container (`_000001`), and Spark 3.5 logs at INFO how it ran the application: `DAGScheduler` (`Got job J (call site) with N output partitions`, `Got map stage job …` under adaptive execution, `Final stage:`, `Parents of final stage:`, `Submitting N missing tasks from <Stage> S (RDD)`, `<Stage> S (name) finished in X s` or `failed in X s due to …`, `Job J finished: …, took X s`, `Job J is finished. Cancelling …`), `TaskSetManager` (`Starting task I.A in stage S.T (TID n) (host, executor E, partition P, LOCALITY, B bytes)`, `Finished task … in M ms on host (executor E) (k/N)`, `Lost task … : reason`), the scheduler backend (`Registered executor`), `BlockManagerMasterEndpoint` (`Registering block manager … with X RAM`), `YarnAllocator` (`Launching container C on host H for executor with ID E`, `Launching executor with … and N cores`, `Completed container`), `ExecutorAllocationManager` (idle removals), `TaskSchedulerImpl` (`Lost executor`), `SparkContext` (version, name, `Successfully stopped SparkContext`) and the application master (`Final app status: …, exitCode: N`). yarnlog keeps these as driver events (`model.DriverEvent`, at most a million per file); when no event log was read, `eventlog.Rebuild` turns the events of the log with the most of them in the latest attempt, if it shows a job started, into the listener events an event log would hold, each with its driver log line as its source, and the parser folds them (`EventLogStats.Layout` `container-logs`). A stage belongs to the job whose final stage or parent it is, otherwise to the job started last and not yet ended; a stage's time is its own "finished in" seconds (to the millisecond) and each task's its "in N ms". The run's executors carry their container IDs, so their logs join as with an event log. Left out: stages a job skipped (not logged), task metrics (rows, bytes, CPU and GC time, spill, memory), SQL plans and Spark's configuration. Sections built from those say they need the event log, the rules that read them do not run, and the summary says the run was rebuilt; the Sources panel has a "Driver log rebuild" row, and the event log stays `not-supplied`. HBase scans in a rebuilt run tie their regions to the rebuilt tasks (any stage may scan, as the driver's log does not name the Hadoop RDD), with rows marked as needing the event log.

**Each task's story, from its executor's log.** An executor logs, at INFO, what each task does (Spark 3.5.1's messages, checked against its source and the fixtures): `Executor` (`Running task P.A in stage S.T (TID n)`, `Finished task … (TID n). N bytes result sent to driver` or `via BlockManager`, `Result is larger than maxResultSize`, `Exception in task …` with the exception on the next line, `Executor killed task …, reason:`), `TorrentBroadcast` (`Started reading broadcast variable N with P pieces (estimated total size X)`, `Reading broadcast variable N took M ms`), `MemoryStore` (`Block rdd_… stored as values in memory (estimated size X, free Y)`, with EMR's `actual size:` too; `After dropping N blocks, free memory is X`; `Not enough space to cache …`), `ShuffleBlockFetcherIterator` (`Getting N (X) non-empty blocks including … local and … host-local and … push-merged-local and … remote blocks`, `Started N remote fetches in M ms`), `UnsafeExternalSorter` and the `Spillable` collections (`spilling sort data of X to disk`, `spilling in-memory map of X to disk`), `HadoopRDD` and `NewHadoopRDD` (`Input split: path:start+length`, or an HBase region), `FileScanRDD` (`Reading File path: …, range: a-b`, and EMR's `TID: n - Reading current file: path: …`) and `SparkHadoopMapRedUtil` (`…: Committed. Elapsed time: M ms.`). yarnlog folds each line into the story of its task (`model.TaskLog`: totals, and up to 40 timestamped steps, each with its line, for the replay): the task its thread names, in a layout that prints the thread; else the task the line names by TID; else, in a layout with no thread, the only task the executor was running then. Lines no task can be found for add up per executor (`Untied`), and the coverage says how many, and that `%t` in the executors' log4j pattern ties them all. On the 0049, 0050, 0084 and 0088 fixtures every task the event log records has a story with the same outcome and result size, and the executors' shuffle blocks add up to the event log's. Shuffle sizes are Spark's estimates from the map outputs (a few percent off; the event log has exact bytes), input sizes are file ranges' lengths, and rows and CPU time are only in the event log. Stories of earlier application attempts are left out (the final attempt reuses their task IDs). The explorer's Task stories view (under More) lists up to 20,000 tasks and a page per task with its steps; the JSON report has every story.

**Data moved and memory over time, from the stories.** Each task's steps, and the steps of lines no task could be found for (up to 20,000 per executor log), are laid out over time in steps of whole seconds (at most 120): shuffle bytes asked for on the task's own node and over the network (when each read began; Spark's estimates), bytes spilled and cached, and per executor its bytes over the network per step and its storage memory free after every block it cached or dropped (the least, and when). Broadcast variables are listed with their estimated size, pieces, the executors that logged reading them, read time in all and the slowest read; spills by stage with the task that spilled most. The explorer's Task stories view charts "Data moved over time" and "Storage memory left over time" (the executors with the least left) and list both tables; the JSON has `flows`. Findings: `shuffle-network` (at least `network-min`, 1 GiB, read over the network: a warning when one executor read at least 3× the median of the others, else a note of the share), `cache-evicted` (cached blocks dropped or that did not fit, which Spark computes again), `broadcast-large` (a broadcast of at least `broadcast-large`, 512 MiB, or one executor's read of at least `broadcast-slow`, 10 s), `task-spill` (without the event log, whose `memory-spill` has exact bytes: at least `spill-min`, 1 GiB, spilled) and `commit-slow` (output commits taking at least `commit-share`, 20%, of the writing tasks' time and at least `min-run-time` in all). Size thresholds take values such as `512MiB` or `1GiB`.

**Replay.** The explorer's Replay tab plays the run back from the task stories and the flows, at the times the logs give. Each executor is a compact card (side by side, in executor order, naming its cores but not its node, which the executor's page names) with a slot per core, or as many as it ran at once, and each task fills the first slot free at its logged start, coloured by stage, labelled with its partition ("p12"; the stage and task in its tooltip, so a long label never spills) and linked to its page (Spark does not log which core ran a task; a task within one logged second is drawn for 400 ms). A legend above the cards names the stage of each colour for the stages running now; the palette has five colours, so stages five apart share one and a slot's tooltip tells them apart. Each card's grey bars (never a stage colour) show its shuffle bytes over the network in the current step and its storage memory left. The driver's panel lists the jobs running (up to 5) and, numbered, the stages running (up to 8, then "and N more"), each with its tasks done of its total. "What happened" is a numbered list, newest first (the 14 latest), each line with its time and a tag (Job, Stage, Started, Finished, Failed, …): tasks of one stage that started, finished, failed or were killed in the same second share a line that opens to list each, and a picker shows jobs, stages and tasks (the default), jobs and stages only, or everything step by step (tasks reading broadcasts, fetching shuffle blocks, reading input, writing files, caching, spilling, committing). Controls: play and pause, restart, next event, a scrubber, and speeds from real time to the whole run in 20 seconds (a minute by default). It starts paused and animates with `requestAnimationFrame`, so it stops with the tab; it uses no data the page does not already carry.

**Verified behaviour.** Checked on real EMR 7.3.0 clusters and fixtures, and relied on by the rules.

- *Spark event log.* Spark 3.5 does not log the driver's exit code, so status comes from the end event, the last job, the driver's `Final app status` line and YARN's summary; Spark closes the log normally even when user code failed outside any job. Cached data sizes need `spark.eventLog.logBlockUpdates.enabled`, process RSS `spark.executor.processTreeMetrics.enabled`, per-stage executor peaks `spark.eventLog.logStageExecutorMetrics`. The driver's heartbeat samples carry stage -1. Speculative, unschedulable and miscellaneous-process events never reach the log. Task times are stamped by the driver, so running tasks can briefly exceed task slots. PySpark records a code location for some actions only (`collect()`, not `count()`, `show()` or `write`); the driver's command line (`sun.java.command` in System Properties) names the script spark-submit ran (`--primary-py-file` or `--primary-r-file` in YARN cluster mode, SparkSubmit's first non-option argument in client mode), kept as `application.script`. Spark stores "average" SQL metrics per task as ten times the value. Library versions come only from jar names (the classpath, and jars shipped with `--jars` in `spark.jars`/`spark.yarn.dist.jars`).
- *Event log on S3.* Spark refuses an S3 `spark.eventLog.dir` with no objects under it (SparkContext never starts, exit 13). A log appears only when Spark closes it: `.inprogress` when the application died, nothing when it was killed with its cluster.
- *EMR and YARN.* `LogUri` uses `s3n://`, and terminated clusters still describe. EMR copies logs to S3 every few minutes while a cluster runs (the ResourceManager's current log about 15 minutes late) and all of them when it ends. Log times carry no zone: they are in the nodes' time zone, UTC unless the cluster was set to another, so `log-timezone` (config file, per environment, or `-log-timezone`) names it. It applies to every log line's time and to the hour in rolled HBase log names; the event log, YARN's application summary (epoch milliseconds), the EMR API and the step controller (times ending in `Z`) are UTC whatever it is. When the container logs' first time is a whole zone (a multiple of 30 minutes, give or take 15) from the event log's start, YARN's summary or the step's start, the console and the Container logs row say log-timezone looks wrong. The console and the HBase logs row show the window in the log zone, labelled. EMR sets the executor overhead factor to 0.1875 without it reaching the event log; the driver's launch line gives the real size. The capacity scheduler places containers by memory alone. Exit codes: the application master's 10 (uncaught exception), 11 (too many executor failures), 13 (SparkContext never started), 15 (user class threw); YARN's negative codes (-104 physical memory, -102 preempted); Spark's executor codes 50–56 (52 out of memory); 143 at every normal executor finish. A heap out of memory also ends in 137: Spark's `-XX:OnOutOfMemoryError="kill -9 %p"` runs after HotSpot prints `# java.lang.OutOfMemoryError` to stdout. The NodeManager checks memory every 3 s, so short spikes pass. The primary node's `master.log` says `bootstrap action 1 failed` on every cluster; only `BOOTSTRAP_FAILURE` in the cluster's state means it. `spark.task.maxFailures=2` clashes with EMR's `excludeOnFailure` default and stops SparkContext. EMR names a spot reclaim in the instance's state reason.
- *CloudWatch and CloudTrail.* EMR publishes cluster metrics every minute; EC2 CPU is every 5 minutes without detailed monitoring, each point stamped with the start of its period; retention is 15 days for 1-minute data and 63 days for 5-minute data. Test clusters had no CloudWatch agent. CloudTrail names an instance profile's session by instance ID, never returns S3 object calls (data events), keeps 90 days, and did not show a refused `AssumeRole` of a role that does not exist.
- *HBase 2.4 on EMR 7.3.* EMR 7 does not ship the hbase-spark connector; connector 1.0.1 needs an SLF4J 1.7 binding and HBase's client needs protobuf 2.5 (`/usr/lib/hadoop/lib/`), which Spark 3.5 lacks. The quorum usually comes from an `hbase-site.xml` shipped with `--files`, so only the ZooKeeper client's `connectString` line shows it. The connector opens about one ZooKeeper connection per task. The client retries expired scanner leases, busy regions and moved regions itself, logging busy retries at INFO (`AsyncRequestFutureImpl … attempt=n/m`); it logged nothing when a region server stopped under a running job, which only the Master's `ServerCrashProcedure` and the region server's `STOPPED:` lines show. The Master writes an empty `ERROR master.ServerManager:` line with every region move. `TableInputFormat` gives no splits for a table whose rows are all unflushed. The event log names only the connector's tables; `TableInputFormat` and `TableOutputFormat` tables and regions are only in the executors' logs.

## 4. Architecture

A pipeline: resolve (cluster, application, window) → access check → collect (S3, local folder, AWS APIs) → parse (event log, logs) → join → analyse → render.

| Package | Responsibility |
| --- | --- |
| `cmd/sparkplain` | Flags, config file, access check, console output, exit codes |
| `internal/sparkplain/source` | `Store` interface with S3 and local-folder implementations: listing, sampling, bounded concurrent fetch, decompression, error classes |
| `internal/sparkplain/eventlog` | Streaming event log decoder (codecs, rolling folders, zips); dispatch on `Event`; per-stage aggregates; the explorer's samples; SQL plans; a field inventory of every Spark 3.5 event field, used or set aside with a reason |
| `internal/sparkplain/yarnlog` | Classifies container, step, node and HBase server logs in one streaming pass per file, folding repeats (up to 500 distinct lines per file) |
| `internal/sparkplain/awsmeta` | EMR, EC2, CloudWatch and CloudTrail clients and their readers; `awsfake` replays recorded API answers in tests |
| `internal/sparkplain/model` | The report's types, serialised as the JSON |
| `internal/sparkplain/analyze` | One analyser per section; the findings rules |
| `internal/sparkplain/report` | `report.html` (the summary: templates and inline SVG built in Go), `explorer.html` (data embedded, charts drawn by the embedded D3), the JSON writer |
| `internal/sparkplain/redact` | Secret redaction and text sanitising, applied before values enter the model |

**Design rules**

- **Stream, never load whole logs.** Task events fold into per-stage aggregates and fixed-size samples. Budget: 60 s and 1 GB of memory per GB of event log, and 1.5 GB per GB when every task's executor log is read too (task stories and flows), both checked in CI (`make bench`, on a synthetic 150,000-task log and, with `scripts/benchlog -logs`, its executors' logs). The binary sets a soft memory limit of 1 GiB unless `GOMEMLIMIT` sets one, so the garbage collector works harder before the heap doubles. Lines are read without backtracking patterns on every line: Spark's header is parsed by hand, and patterns that cannot start with a fixed word are tried only when a word they need is in the line.
- **Provenance.** Every value records its source file and line (or API call); every finding cites its evidence and, where it applies, the stage, job, executor or node it concerns.
- **Degrade, don't fail.** A missing, refused or unreadable source is a Sources row with its reason; its sections say what they lack; the run exits 3.
- **Secrets never reach the output.** Keys matching password, secret, token, key or credential are redacted in configuration and log lines; free text loses matching `key=value` pairs, URL passwords and AWS access key IDs; source code loses every string on a line naming a secret, except the key. Tests plant fake secrets and assert they never appear. Some harmless Hadoop settings with "key" in their name are hidden too, deliberately.
- **Tests never call real AWS.** Clients sit behind interfaces; the test fakes fail if any client is left unstubbed.

## 5. What the report shows

The analysis covers the sections below; the JSON has all of them. The report page is a short summary: What happened, The run at a glance, Findings, What this report covers (the coverage of every section) and Sources. Every other section is in the explorer, which the report links to: Timeline (Timeline tab), Cluster and nodes (At a glance), Executors, Memory and CPU (Executors), Storage and I/O and Jobs, stages, SQL (Stages, SQL / DataFrame, and the HBase views under More), What each task did (Task stories), Configuration and Identity and access (Environment). Each summary section and each coverage row opens the matching explorer tab ("Open in the explorer →"), and the report's menu lists the explorer's detail under "More in the explorer"; without an explorer page there are no such links.

| Section | Answers | Main sources |
| --- | --- | --- |
| What happened | Two to four plain sentences: outcome, scale, data moved; the warning and critical findings that need attention as a short list of their titles (at most three) | All |
| The run at a glance | A diagram of the run at its busiest: the cluster; a "Cluster capacity used" card with a bar and one plain fact per bullet (what the cluster had, shown as worker nodes × what each gave YARN with the two settings that set it, `yarn.nodemanager.resource.memory-mb` and `yarn.nodemanager.resource.cpu-vcores`; what this application used of its memory and vCPUs and what was left; how many containers waited and for how long, with no reason claimed, the finding giving it; and whether other applications shared the cluster), long bullets wrapped and the card sized to them; a key naming each colour and mark it uses, each worker node that ran the application's driver or executors with a CPU row and a memory row, each led by a grey icon drawn in the page (a chip, a memory stick): CPU as a small bar to CloudWatch's average with a tick at the peak, the two in words and a sparkline of the run, and memory as what this application held of what the NodeManager offered YARN, above its containers to scale and labelled with their size (unused space hatched; these nodes are never folded into "more like it", and are laid out in executor order: a node that ran only the driver first, then the node of executor 1, then the node of the lowest executor not yet shown, and so on), the worker nodes it did not use as one box counting them by role and instance type with what they offered YARN and how many came or went during the run (when the run says which nodes it used; otherwise every node as before), each executor's cores (dark pink squares, always outlined so an idle core still shows on the executor's pale card, the more solid the busier; the only pink in the diagram, off-heap and Python memory sharing overhead's amber as memory outside the heap), container size and peak heap (executor cards in the executor containers' blue; a node that ran more executors than three rows of cards hold draws them as small tiles in the same colours, each with its ID and its peak heap as a bar, the rest in its tooltip), one executor and the driver region by region; findings pinned as numbered badges on the part they concern | Event log, logs, EMR, CloudWatch |
| Findings | Every finding, most severe first, each with explanation, evidence and fix | All |

**HBase block** (Storage and I/O, when the run used HBase): tables read and written and how (hbase-spark connector from SQL plans; `TableInputFormat`/`TableOutputFormat` from executors' logs); regions read per region server; the ZooKeeper quorum and connections opened (in all, and the most by one process); client and connector versions; the stages that used HBase with their time, CPU share, the client retries logged while they ran and the server events that hit them; regions read on their own node; and what the HBase servers logged during the run, marked when it concerns this run (one of its tables, a scan from one of its executors, or a whole region server), since those logs are the whole cluster's. Each count in a stage's retries cell names a line behind it (file:line).

**HBase scans** (in the HBase block, and on the stage's page in the explorer), one per `TableInputFormat` stage (a `NewHadoopRDD` from `newAPIHadoopRDD`): the key range its regions cover; regions read, on how many region servers, and each server's regions, rows, estimated size and task time; rows returned (the event log's input records; Spark counts no bytes for HBase input); the size TableInputFormat estimated (`Input split length`); and each region with its key range, region server, rows, time, executor and task. The regions come from each task's `Input split: Split(tablename=…, startrow=…, endrow=…, regionLocation=…, regionname=…)` line. TableInputFormat makes one split per region in key order and Spark's partition *n* reads split *n*, so a stage's splits sorted by start row are tied to its partitions. When the log layout prints the thread, each split line names its task, and when it does not (EMR's default) a split line logged while its executor was running only one task (between that task's `Running task` line and its end, as on one-core executors) belongs to that task, with its size line and its time (Spark's `Executor task launch worker for task <partition>.<attempt> in stage <stage>.<attempt> (TID <tid>)`), and a scan whose every split does is tied by task, exactly (`tiedBy: "task"`); otherwise by key order (`tiedBy: "key order"`), only when the splits and the stage's tasks match one for one and every split was logged by the executor that ran that partition, and otherwise rows and time per region are left out with the reason. A size line is tied to its split by the task its thread names; in a layout with no thread, only when no other task's lines interleave, or when every size in an interleaved group is the same (executors run tasks at once). The explorer says which tie was used. Without the event log, a scan is built from split lines that name their tasks: the stage and partition come from the thread, each region's time runs from its task's `Running task` line to its `Finished task` line (to the millisecond, in the thread-first layout), a partition that ran more than once keeps the attempt that finished, a task with no end or only failed attempts shows no time, the executor comes from its log's `Starting executor ID <n> on host <host>` line, and rows are marked as needing the event log; `hbase-scan-skew` then weighs the slow region by its estimated size rather than its rows. Split lines that name no task are listed as missing, since only a layout that prints the thread places them without the event log. The explorer shows such a scan on its own stage page, linked from the Stages view.

**HBase tasks** (in the HBase block, the explorer's HBase tasks view under More, and `hbase.tasks` in the JSON): every `TableInputFormat` task attempt the executors logged a split for, across all stages, one row per attempt, in stage, partition and attempt order (what is not known last): stage, task (partition.attempt), TID, table, start and end row, region, region server, executor and host, started, ended, took (and whether from the executor log or the event log), outcome (finished, failed, no end logged), estimated size, rows (with the event log only), and the lines behind it. The task comes from the thread named on the split line, or the only task its executor was running or, with the event log, from the scan's tie; a split line with no task in a stage tied by key order gets the region's task only on the last line its executor logged, since earlier lines were other attempts. The event log's task (rows, time, executor) is used when it records that attempt (one successful attempt per partition). A table per stage above it sums the attempts, failures, regions, region servers, and first start and last end. The explorer shows up to 50,000 rows, the JSON all.

**Region server load over time** (in the HBase block, and in the explorer's HBase tasks view): from each task's start and end in the tasks table (its Running and Finished lines, or the event log's launch time and duration), how many `TableInputFormat` tasks each region server served at once, as a step chart of the most at once per step (at most 240 steps of whole seconds) for the busiest servers and all of them together, and a table per server: tasks, task time, time at least one ran (busy), the most at once and when, task time over busy time, and the longest stretch it served at least `hbase-hotspot-share` of the scan tasks running (and at least 4) when the run read more than one server. `hbase-server-load` reports the longest such stretch of at least `hbase-load-min` (1 min).

**What the region servers logged about the regions read** (in the HBase block, and in the explorer's HBase tasks view): HBase's servers name a region by its encoded name (32 hex digits, the last part of its full name), the same as the split lines' `regionname`. From the Master's and region servers' logs, sparkplain keeps what they said about single regions during the run: `Finished flush of … for <region> in <n>ms`, `Completed compaction of <n> file(s) in <region>/<family> … took <n>sec`, `Close <region>` and `Opened <table>,…,<ts>.<region>.` (a close and the next open become one *offline* event, the time it served no reads), the Master's `move hri=<region>, source=…, destination=…` and `SplitTableRegionProcedure … parent=<region>`, refused writes (`RegionTooBusyException … regionName=<region>`, in the exception under the warning), and slow calls (`(responseTooSlow)` with `region= …<region>.` in its parameters; not on the fixtures). The same event on the same region and server a minute apart at most is folded and counted. An event is tied to the run's tasks reading its region at the time (within a second, as server log times have whole seconds); events tied to no task are left out. A task is *slow* when it took at least twice its stage's median and `skew-min-task` more. The table lists events on slow tasks' regions first (report: 200 rows), and each task's row in the tasks table names what its server logged. `hbase-region-events` reports slow tasks whose region was compacting, offline, moving, splitting, refusing writes, answering slowly, or flushing for 10 s or more while they read it, with a fix for each kind. The scan as the job defined it (key range, columns, settings, filter tree; decoded as `-decode-scan` does) is shown when a scan string is available: a `sparkplain-scan {"table": …, "scan": …}` line the driver printed (container stdout, or the step's stdout in client mode), decoded as it is read so the string itself (with its filters' values) is never kept, or a `hbase.mapreduce.scan` Spark property. `hbase-scan-skew` reports a scan whose slowest region took at least twice the median region and at least `skew-min-task` longer, naming the region, its server and its share of the rows.

**Exit codes:** 0 complete; 2 fatal (usage mistakes, a cluster or file that does not exist, an `-app-id` that does not match, output that cannot be written); 3 partial (a source missing, unreadable or refused); 130 interrupted.

**No access is not fatal.** A refused permission or bad credentials leave the rest of the run intact: the source is printed on stderr with the permission it needs, listed at the top of both pages, recorded in `report.json` (`accessGaps`) and marked `accessDenied` in the Sources panel; the run exits 3. Without `DescribeCluster`, an online run still reads an event log given to it. A missing `-profile`, a malformed application ID and a cluster that does not exist still exit 2.

**IAM permissions:** `s3:ListBucket` and `s3:GetObject` on the log and event log buckets (`kms:Decrypt` for SSE-KMS); `elasticmapreduce:ListClusters`, `DescribeCluster`, `ListInstances`, `ListInstanceGroups`, `ListInstanceFleets`, `ListSteps`; optional `elasticmapreduce:DescribeStep`, `DescribeSecurityConfiguration`, `ec2:DescribeInstanceTypes`, `cloudwatch:ListMetrics`, `cloudwatch:GetMetricData`, `cloudtrail:LookupEvents`.

In colour, numbers and their units (`527`, `1.7 MiB`, `39 s`, `17×`, `86%`) are cyan, while digits inside names and paths (`application_…_0042`, `ip-10-0-2-13`, `/out/001`) are left alone. When the console is not a terminal (a script, `nohup`, CI), a step still running after 30 s says so on stderr every 30 s (`sparkplain: still reading container, step and node logs (2 min 0 s, 45% · …)`), so a log shows the run is alive. Before `Done in`, a `Took` line lists the steps that took a second or more, slowest first (event log, cluster logs, HBase logs, CloudWatch, CloudTrail, code, rebuild, analysis, report, explorer, JSON), so a long run shows where its time went. On a colour terminal the console is animated, saying the same text: the status line spins with a running clock, each source's mark settles into its dot, findings' dots grow in, the title's diamond fills in, sections come a second apart and a rule sweeps across before the last line (about 5 s in all). A CI environment or `SPARKPLAIN_NO_ANIMATION=1` keeps it still, as does anything that turns colour off. Piped, or with `NO_COLOR` or `TERM=dumb`, there is no colour and the marks are Y, N, !, ? and - (findings !!, ! and -), so logs and scripts stay plain; notes keep their `sparkplain:` prefix on stderr. Symbols are single-width, so columns line up. Lines wrap at `COLUMNS` (80, at most 120); a path too long to share its line gets one of its own, and `try:` commands are never wrapped.

**Report page.** The summary sections in §5. The text on both pages follows ASD-STE100 Simplified Technical English as `docs/STYLE.md` applies it (quoted log lines, Spark's names, configuration keys, paths and IDs excepted), and `TestPlainLanguage` checks what a program can: sentences of at most 25 words (20 for an instruction), no contractions, no words STE does not approve. Every chart and graph (the run at a glance on the report; every chart in the explorer) has a title and, under it, the same guide: what each axis or mark stands for, one labelled line each (Across, Up, or Rows, Bar length, Colour, Boxes for charts that are not x against y); how to read it, as bullets when there is more than one point; "In this run", worked out from the analysis (`runNotes`): what this run's chart shows (the longest stage, the worst straggler that cost at least a second, the stage that lost most time to anything but computing, a node that ran only the driver and why, idle nodes, slot use, driver gaps, spill, peak heap), each finding the chart is evidence for linked by number, or "Nothing unusual here"; and fine print such as sampling or what was left out (a test enforces it); every metric has a one-line explanation and shows used against available; every section shows its coverage (complete, partial, needs the event log) and what is missing. Findings read in three bands: what went wrong, the evidence, what to try. Each finding folds under its number, severity and title, on both pages: critical and warning findings start open and info findings closed; "Open all" and "Close all" act on the list; a link to a finding opens it; printing opens every fold and then puts them back. The report's coverage table folds under a count of its statuses (for example "11 parts: 2 complete, 9 partial"). Headings make an outline with no level skipped (one h1, an h2 for each section, an h3 for each part); the labels of a chart's guide and of a finding's bands are headings one level down, styled as small labels. Tables scroll in their own box with pinned headers. Times show in the config file's `timezone` (default the local zone), labelled, and the page relabels them in the viewer's zone; JSON times are UTC.

**Explorer page.** A per-application take on the History Server's tabs, linked both ways with the report. Tabs: Overview (what happened, findings, the chain that held up completion, what the run used, the stages worth a look (the same ranked list, top 8), charts over time), At a glance (the diagram of the cluster and its nodes, then "Inside executor N" and "The driver" as sections of their own, each drawn region by region with its own guide; the report keeps both at the foot of its diagram; clicking an executor's card opens it drawn in full above the diagram, as the diagram draws one executor, with its own heap, peaks, cores and findings, and a link to its page; up to 300 executors are drawn), Timeline (queries, jobs, stages, executors, tasks against slots and node CPU on one zoomable axis), Replay (when the executors' logs told the tasks' stories: the run played back), Jobs, Stages (worth a look first: a ranked list, failed stages, then those on the critical path, then those with stragglers, disk spill or a retry, then the rest, longest first within each, each row with one duration bar on a shared scale and its reasons in words, the critical-path reason left out when most stages are on the path; then duration, data, time, spill and skew views, and time against data as a scatter only when at least two stages handled data; per stage: quartiles, histogram, task scatter with selectable axes and colour, slowest tasks, per executor, operation graph, code), Executors (stage × executor heatmap first), SQL / DataFrame (plan graph with operator metrics), Cluster (online runs), and under More: Storage, Code, Environment (identity and access first: users, queue, Kerberos, catalog, security settings and what is not shown yet; then versions and settings), Event log, Logs (the cluster, its log URI and instance profile, and the nodes up during the run, the same ones At a glance counts, by role (primary, core, task) and numbered within it, with the count of all instances the cluster has had; then each log read), HBase tasks, Task stories. On the Logs tab each source folds under its name and status (a source not read in full starts open), and the Environment tab's setting groups have "Open all" and "Close all" beside the search. Each tab has an "On this page" list of its parts: its h2 and h3 headings and its charts' titles, not the labels in guides and findings, and none for a tab with fewer than two parts. It never takes width from the page: when the window is at least 1,800 px wide it is fixed in the empty margin left of the page, and otherwise it is a folded box above the tab; a click scrolls to the part and leaves the address, which names the tab, as it is. Each tab's heading levels are closed up, so none is skipped. Charts are drawn by the embedded D3 7.9.0 (pinned by hash) through a small kit in `explorer.js`; a chart that cannot be drawn says why and the rest works. Graphs are laid out in Go. Code is highlighted by a small built-in highlighter that builds text, never HTML. Embedded JSON is escaped so no value can close the script tag.

Explorer data is collected while streaming, within the memory budget: per-stage quartiles and log-scale histograms; per stage the 100 slowest tasks and a uniform sample of 1,000 (fixed seed), 100,000 sampled tasks at most in the app (halved by subsampling past it; charts drawn from samples say so); stage × executor totals (1,000,000 cells); running tasks in time buckets (2,000); SQL operator metrics; log lines (200 per file, 5,000 in all). The page stays under 25 MB at the defaults. This data is only in `explorer.html`; `report.json` keeps everything else.

**JSON.** Mirrors the model package, with a `schemaVersion`. It is written compact, not indented (`jq .` indents it), and the task stories are streamed into it one at a time, so the file is never held in memory whole.

## 7. Limitations

The report states these plainly rather than hiding them.

| Limit | Effect |
| --- | --- |
| The event log is on HDFS by default and dies with the cluster | The run is rebuilt from the driver's log (jobs, stages, tasks, executors) without task metrics, which need the event log; the run explains how to supply it |
| EMR copies logs to S3 only every few minutes while a cluster runs | A recent run can lack logs; the access check and Sources say so |
| Executor memory is sampled (heartbeats and stage peaks) | Short spikes are missed; charts say "peak" |
| Host memory and disk need the CloudWatch agent | Shown only when present |
| Shared clusters run several applications at once | Node and HBase server figures are cluster-wide and marked as such |
| CloudTrail covers management events for 90 days | No S3 object calls; no calls under a step's runtime role |
| Newer Spark releases may add event fields | Unknown fields and events are counted and shown, not lost |
| Clocks differ between nodes and services; log times have whole seconds | The event log is the reference; log lines go to the stage that started last before them |
| The HBase client logs nothing for some problems | HBase's server logs fill the gap; region moves under a running job, region server timeouts, pauses, slow calls, aborts and HBase access refusals were never seen on a real run and are tested with HBase 2.4's own messages |

## 8. Delivery

All five phases are built. Plans, step notes and live checks are in [HISTORY.md](HISTORY.md), which is where new plans go before they are built; this spec is then updated to match.

| Phase | Delivered |
| --- | --- |
| 1. Event log core | The report from the event log alone; the 1 GB budget |
| 1b, 1c, 1d, 1e, 1f | The explorer; every event field used or set aside; offline charts; diagnostic views; curation |
| 2. Online mode | Fetching from S3 and the EMR API; container, step and node logs; the first failure |
| 3. AWS enrichment | Instances, CloudWatch, CloudTrail, security configuration |
| 4. Findings and polish | Every rule tested; the CI benchmark; recorded AWS fixtures |
| 5. HBase | HBase failures told apart; HBase use and slowness; HBase server logs |
| Access check | What a run can read, before it reads it; `-check` |
| 6. The run from its container logs | The run rebuilt from the driver's log; each task's story from the executors' logs; data moved and memory over time, and their findings; the run replayed in the explorer |

Testing: stubbed S3 and AWS clients, recorded AWS answers replayed from `testdata/aws/`, scrubbed fixtures from real EMR runs, planted secrets, the race detector on the packages that start goroutines (`RACE_PKG`), fuzz targets for the decoder and classifiers.
